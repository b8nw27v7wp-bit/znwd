# 知识库维护

展厅讲解的知识全部来自 `knowledge/` 目录：改这里的内容 → reload → 抽查 → 重新标定 → 跑评测，是全套流程。

## 1. 目录与展区

```
knowledge/
├── _meta/
│   ├── zones.json          展区、别名、推荐问题、媒体映射（不进入检索）
│   └── synonyms.tsv        同义词覆盖表（可选；不进入检索）
├── 01_光伏清洁机器人/       zone = pv-clean
├── 02_光伏医生运维系统/     zone = pv-doctor
└── 03_项目与团队/           zone = project
```

当前 3 个展区、1 个展项（`media`）：

| zone id | 目录 | 展区名 | 别名（关键词也按这些加权） | 推荐问题 |
| --- | --- | --- | --- | --- |
| `pv-clean` | `01_光伏清洁机器人` | 光伏清洁机器人 | 光伏 / 清洁 / 清洗 / 机器人 / 履带 / 组件 | 3 条 |
| `pv-doctor` | `02_光伏医生运维系统` | 光伏医生智慧运维 | 光伏医生 / 巡检 / 诊断 / 数字孪生 / 热斑 / 积灰 | 3 条 |
| `project` | `03_项目与团队` | 项目与团队 | 团队 / 专利 / 获奖 / 市场 / 背景 / 合作 | 3 条 |

媒体映射：`exhibit-pv-clean` → `pv-clean`。

替换正式资料时**保持目录 id 与 `zones.json` 的 `dir` 一致**即可，不用改代码。

## 2. 文件格式

Markdown，可选 YAML frontmatter：

```markdown
---
title: 光伏清洁无人机产品概述
zone: pv-clean
tags: pv-clean,光伏,清洁
---

## 产品定位

……
```

| 字段 | 作用 |
| --- | --- |
| `title` | 块标题（缺省时用文档内第一个 `#` 标题或文件名） |
| `zone` | 显式指定展区；**不写时按顶层目录名匹配 `zones.json` 的 `dir` 自动推断** |
| `tags` | 逗号/空格分隔，命中时参与打分（权重同展区名） |

其它 frontmatter 键（如 `source`、`ingestedAt`）会被忽略但无害。
`_meta/` 下的文件**不进入检索**（展会元数据与占位文档都在这里）。

## 3. zones.json

```json
{
  "zones": [
    { "id": "pv-doctor", "dir": "02_光伏医生运维系统", "title": "光伏医生智慧运维",
      "aliases": ["光伏医生", "巡检", "诊断", "数字孪生", "热斑", "积灰"],
      "suggestions": ["光伏医生系统是什么？", "无人机巡检能发现哪些故障？"] }
  ],
  "media": [{ "mediaId": "exhibit-pv-clean", "title": "光伏清洁无人机展项", "zoneId": "pv-clean" }]
}
```

- `aliases` 参与关键词打分（命中展区名的块加权），也是 `/api/suggestions` 匹配用的键之一。
- `/api/suggestions?zone=<zoneId 或 mediaId>`：先按 `mediaId` 映射到所属展区，再按 zoneId / 目录名 / 别名匹配；不传 zone 返回全馆汇总。**返回的 `items` 是字符串数组**。
- 文件缺失或损坏时退化为空展区（不阻塞启动），`/api/zones` 会返回空列表。

## 4. 分块规则

| 规则 | 值 |
| --- | --- |
| 硬边界 | 以 Markdown 标题（`#`~`######`）分段 |
| 段内打包 | 段落合并到 **500 字符**上限 |
| 超长段落 | 按 **500 字窗口 / 80 字重叠**滑窗切分 |
| 块标题 | 每块带所在标题；同一标题的后续块标「标题（续）」+ 正文，避免脱离上下文后语义漂移 |
| 块 id | `<相对路径>#<序号>` |

**一篇长文会被切成多块**（当前 219 块、17 篇）——这是为什么来源列表里可能看到同一文档的多条：每一块算一条来源（与旧实现一致）。
写作时**用 `##` 分节**、每节一个主题，检索精度会明显更好；把整篇写成一个超长段落反而会被滑窗切碎。

**问句式小节标题（实测最有效的一招）**：把访客的原话问句直接做 `##` 标题，答案只写原文事实。
分块会把小节标题写进块正文（`标题\n\n正文`），标题因此参与正文打分（权重 1.0、受长度归一），
而文档级 `title`/`tags` 命中按 2.2 / 1.0 加权且不做长度归一——所以关键名词放进 `title`/`tags`、
访客措辞放进小节标题，两条路一起用。实测：语料换成公司自有材料后，靠这一招把在域用例的闸门误拦从 8 条降到 0
（阈值后来单独从 8.1 调到 6.3，依据是真实问句口径的取舍表，见 `docs/eval.md`）。
反例：把关键词在正文里反复堆砌是噪声，`maxTfBoost` 就是为压它而存在的。

**每个展区再放一篇「常见问题」**：访客口语问句最集中的地方，一节一问（`## 这问题怎么问就怎么写`），
答案只写原文事实、可以与前文重复。实测：只靠 3 篇 FAQ 文件（119 → 192 块），101 条真实访客问句里被闸门拦掉的
从 51 条降到 5 条。为什么必须单独一层：口语问句用的词（有多重 / 有客户了吗 / 有多少人）与正文的书面词
（整机重量 / 客户数量 / 团队）几乎不重叠，正文写得再全也匹配不上。

## 5. 检索与打分

```
问题 ──▶ 关键词路（中文 bigram + IDF + 加权，同义词扩展）
      └─▶ 向量路（bag 特征哈希 / openai_compat 真语义）
                └─▶ RRF 融合 ──▶ 相关性闸门 ──▶ 命中 or 「资料中没有」
```

| 项 | 当前值 |
| --- | --- |
| 关键词打分 | 标题 ×2.2 + 展区标签 ×1.0 + 正文 ×1.0（`ScoringOptions`） |
| 词条权重 | IDF 加权；词频增益封顶（长文档靠反复出现泛词取胜是噪声） |
| 中文切分 | **bigram**（单字不给分：否则「今天上海天气怎么样」会比很多真问题分还高，什么都能答）；**不跨标点/空格边界取相邻二字** |
| 同义词扩展 | 扩展词按 **0.45** 降权（扩展是提示不是要求），原查询词权重 1；表里只放同义词与同域复合词，**不放话题联想词** |
| 向量路 | `EMBED_PROVIDER=bag`（特征哈希，`semantic=false`，不参与融合）或 `openai_compat`（真语义；**只做诊断与「关键词不过闸门时的余弦兜底」，不参与普通查询排序**——实测参与会把 top1 顶掉两例，见 `docs/architecture.md` §3） |
| 融合 | RRF（两路都命中时有微小加成；仅兜底路径生效）。兜底时语义命中是**新增候选**——向量独有的条目直接进融合结果，不是只对关键词候选重排（已决策：文档对齐代码，见 `docs/architecture.md` §3）；线上问答与诊断都走带闸门的调用，新增候选还要余弦 ≥ `MIN_VECTOR_SCORE`，而它当前 = `0.75` = 等效关闭，所以生产实际走不到这一步 |
| 闸门 | 关键词最高分 < `MIN_RELEVANCE_SCORE`（当前 **6.3**）且语义余弦 < `MIN_VECTOR_SCORE`（当前 **0.75** = 关闭兜底）→ `noHit=true` |
| 来源面板 | 命中片段先按**资料文件**去重、再剔除关键词分低于本次最高分 50% 的块（`RagPipeline.SOURCE_KEEP_RATIO`）——门槛用关键词分而不是融合分：RRF 融合分在相邻名次间几乎无差别（实测 0.0164 / 0.0161 / 0.0159） |

四条硬规则（都是踩过的坑）：

- **bigram 不跨边界**：早先把整段文字的单字抽出来连成一条链，于是在标点处造出「测外」（「叶片检测？外观…」）；
  同义词扩展把备选词拼成一个字符串再切更糟——「组件 电站 清洗 积灰」造出「件电」「灰清」，
  这些不存在的词条带着真实 IDF 参与打分，是「域外问题被放行」的直接来源。
- **同义词表不放话题枢纽**：曾经的「光伏 → 组件/电站/清洗/积灰/清洁」让一句「光伏和风电哪个更赚钱」
  靠表里的 5 个泛词攒到 10.96（高过在域最低 8.93）被放行。跨话题的联想应该靠语料和语义向量，
  不能塞进同义词表；改完这类条目必须重新标定阈值。
- **非语义向量不参与排序融合**：`bag` 是哈希兜底、不是相似度，融进去只会打乱关键词路排序，而 `mode` 仍如实上报 `keyword`——上报与行为不一致最难排查。
- **闸门拦截时不调用大模型**：拒答文案固定（`provider=gate`、0 token）。实测让模型生成拒答要 780 tokens 且多等 4.7 秒，纯浪费；要模型措辞时设 `NO_HIT_LLM=true`。

排查某句话为什么被拦，直接问诊断接口（走线上同一套阈值）：

```bash
python -c "import json,urllib.parse,urllib.request as u; q=urllib.parse.quote('帮我写一首关于夏天的诗'); d=json.load(u.urlopen('http://127.0.0.1:8787/api/admin/diagnostics?q='+q)); print(d['verdict'], '| 距阈值', d['distanceToGate'])"
```

（中文用 Python 发：GBK 控制台下 curl 会把参数编坏，表现为"什么都被拦"。）

## 6. 同义词维护

内置 30 组（`Synonyms.java`，含「叶片/风叶/桨叶」「巡检/检查/缺陷/裂纹」等），可用外部覆盖表替换或在线维护——**改完对下一个问题立即生效，不需要重建索引**。

1. **覆盖表文件**：`knowledge/_meta/synonyms.tsv`

   ```text
   # 主词<TAB>备选词（逗号分隔），一行一条
   叶片	风叶,桨叶
   塔筒	塔架,风机塔
   ```

2. **在线接口**：

   ```bash
   # 看当前生效的表（含来源：builtin 或文件路径）
   curl -s http://127.0.0.1:8787/api/admin/synonyms -H "authorization: Bearer $ADMIN_TOKEN"

   # 整表替换（persist=true 写回 synonyms.tsv；false 只改内存）
   curl -X PUT http://127.0.0.1:8787/api/admin/synonyms \
     -H "authorization: Bearer $ADMIN_TOKEN" -H "content-type: application/json" \
     -d '{"entries":{"叶片":["叶片","风叶","桨叶"],"塔筒":["塔筒","塔架"]},"persist":true}'
   ```

规则与坑：

- 覆盖表存在就加载；**文件被删掉后 `POST /api/knowledge/reload` 会退回内置表**（避免"文件删了还生效"）。
- 表不能为空（空表会被拒），否则等于把检索能力悄悄砍掉一半。
- 覆盖表损坏不会把服务带下去：保留当前生效的表并在日志报错，等人来修。
- 改完同义词要**重跑标定与评测**——扩展词会改变分数分布。

## 7. 改知识后的必做流程

```bash
# 1) 写/替换 knowledge/<展区目录>/*.md（frontmatter + 用 ## 分节）
# 2) 重载（重建关键词 + 向量索引，清空答案缓存）
curl -X POST http://127.0.0.1:8787/api/knowledge/reload -H "authorization: Bearer $ADMIN_TOKEN"
# 3) 核对装载结果
curl -s -H "authorization: Bearer $ADMIN_TOKEN" http://127.0.0.1:8787/api/knowledge/list   # chunkCount、retrieval.mode、各文件块数（需管理口令）
# 4) 抽查一在域一域外：在域应 gated=false，域外应 gated=true 且 distanceToGate>0
# 5) 重新标定（阈值是相对量：chunk 数一变，IDF 跟着变、分数整体平移，不重标就可能把该答的问题拦掉）
cd server && ../tools/mvn -B test-compile exec:java@calibrate
# 6) 阈值要改就四处同步：.env / application.yml 默认值 / HybridRetriever 默认常量 / CI 环境变量
# 7) 评测确认不退化
cd server && ../tools/mvn -B test-compile exec:java@eval -Dexec.args="--no-write"
# 8) 契约冒烟
python tools/smoke.py
```

## 8. 资料入库（PDF / Word / txt）

工具：`exec:java@ingest`（旧 Node 版 `server/scripts/ingest-docs.ts` 的 Java 版）。

```bash
# 把 ./inbox 下的 PDF / docx / txt / md 收进「光伏医生运维系统」展区；先 dry-run 看目标路径
cd server && ../tools/mvn -B -q test-compile exec:java@ingest \
    -Dexec.args="--src ./inbox --zone pv-doctor --dry-run"
# 确认无误后去掉 --dry-run 真入库（目标已存在时默认报错，--force 才覆盖）
cd server && ../tools/mvn -B -q exec:java@ingest -Dexec.args="--src ./inbox --zone pv-doctor"
```

| 参数 | 说明 |
| --- | --- |
| `--src` | 源目录（默认 `./inbox`，递归；仓库里没有 `inbox/` 就自己建一个） |
| `--zone` | 展区 id 或目录名（见 `knowledge/_meta/zones.json`），未知值会列可选项 |
| `--knowledge` | 知识库目录（默认 `./knowledge`），验证时指向临时目录用 |
| `--force` | 覆盖已存在的目标文件 |
| `--dry-run` | 只打印将写入的路径与字数，不写盘 |

转换方式：**PDF** 走 `pdftotext -layout -enc UTF-8`（**没有文字层的扫描件会明确报错**，不会产出空文件，请先 OCR）；
**DOCX** 由内置解析器读 `word/document.xml`（保留标题层级、列表、表格，不需要 python 或 Office）；
**txt/md** 直接读；旧版 `.doc` 明确拒绝（先另存为 .docx/.txt）。
三个来源都要过同一套规范化：丢页码与分隔线、合并 PDF 逐行断行（英文补空格、中文直连）、短行升级为 `##` 标题、表格行贴在一起。

产出落在 `knowledge/<展区目录>/<文件名>.md`，frontmatter 由工具生成：

```yaml
---
title: 作业手册
zone: pv-doctor
zoneTitle: 光伏医生智慧运维
tags: pv-doctor,ingest
source: 作业手册.docx
ingestedAt: 2026-09-21
---
```

入库后自检清单：

1. **标题层级**：主题用 `##`；确认转换没有把标题降级成加粗文本（那会导致整篇被当成一个大段落滑窗切碎）。
2. **去掉噪声**：页眉页脚、页码、PDF 断行造成的碎行、分隔线；英文/数字之间补空格。工具已做一遍，抽一眼产物。
3. **表格**：转成 Markdown 表格（纯文本列的表格会被当正文，检索仍能命中，但人看着差）。
4. **编码**：UTF-8；中文文件名可用（`title` 用文件名，注意**块 id 含相对路径**，别在文件名里放空格与特殊符号）。
5. **frontmatter**：`title` / `zone` / `tags` 工具已填；手工落盘的文件 `zone` 不写就靠目录名推断，目录名必须与 `zones.json` 的 `dir` 一致。
6. **扫描件**：没有文字层的 PDF 会被工具拒绝——先 OCR（见技能 `ocr-and-documents`）。
7. **正文里不留「待替换/示例/来源」这类说明**：正文每一行都会被切块、被检索、被当资料展示在「来源」面板上，
   也会被模型念出来（实测把「（示例：bd@example-drone.local）」当真实联系方式答给参观者）。来源、演示标记、
   待办说明一律放 frontmatter（`source:` / `demo:`）或 `knowledge/_meta/` 下的说明文件里。

入库后按第 7 节的流程走一遍，别跳过标定与评测。
