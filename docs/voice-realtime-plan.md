# 全双工实时语音（第 3 档）规划

规划文档，不含实现。目标是把语音问答从「点按 + 分段」升级到豆包语音模式那种**持续听、流式识别、边生成边播、随时插话**的全双工体验。本文只定路线、分期与验收口径；具体接口以选定供应商的文档为准。

前置：第 1 档（VAD 自动断句）与第 2 档（边流式边朗读）已落地，是本文的基线——它们不改后端，本文之后的一切都建立在这两档提供的现场数据与句级朗读队列之上。

## 1. 目标与现状差距

| 能力 | 豆包语音模式 | 当前（第 1/2 档之后） | 差距 |
|---|---|---|---|
| 触发 | 持续听，说话即始、停顿即止 | 点一下进聆听，VAD 停顿 ≈1s 自动收尾 | 已很接近；差**免点按常开**与**服务端端点检测** |
| 识别 | 流式，边说边出字 | 整段录完一次性 POST 识别 | 首字延迟 = 录音时长 + 整段识别耗时 |
| 回答开口 | 边生成边合成，1~2s 开口 | 攒够完整句即合成开播（第 2 档） | 已接近；差**词级流水线**（当前最快 = 一句的生成 + 一句的合成） |
| 打断 | 说话即插话，AI 让口 | 流式期间麦克风禁用，朗读中需点停 | **完全缺失**，本档核心 |
| 全双工通道 | 一条实时音频流 | 麦克风录音 / TTS 播放是两个互斥的 HTTP 时序 | 需要 WebSocket 或等价实时通道 |

## 2. 当前架构约束（事实，改动前先读）

- **后端是 Spring MVC + `SseEmitter` 阻塞式**（`ChatController` 的 `/api/chat/stream`，`sseExecutor` 独立线程池），全仓库 **没有任何 WebSocket / WebFlux / reactor 依赖**（`pom.xml` 只有 `spring-boot-starter-web`）。实时通道要从零引入。
- **MiMo 语音接口是整段 HTTP POST**（`MimoSpeechModel` 走 `/v1/chat/completions`）：ASR 收整段 WAV 回整段文本，TTS 收整段文本回整段 WAV，**均不支持流式**。流式 ASR/TTS 要么换供应商，要么确认 MiMo 是否提供 realtime 端点。
- **单机 Windows 一体机**：jar 自托管静态资源与 API，无外层网关；跨机访问才有 nginx，SSE 需要 `proxy_buffering off`，实时通道额外需要 `Upgrade`/`Connection` 头（deployment.md 尚未写这条）。
- **出口白名单**：`tools/offline-check.py` 维持「除 LLM、embedding、可选语音服务外一律本地」不变量；接新语音供应商 = 改白名单与 `AUDIO_PROVIDER` 语义（security.md 口径）。
- **麦克风依赖安全上下文**（HTTPS 或 localhost），`http://内网IP` 下按钮直接不出现（README 已有提示）。
- **限流现状**：`chatRateLimiter` 30/min/IP（识别与提问共用）、`speechSynthRateLimiter` 60/min；实时长连接的计费/限流维度与「每请求一次」完全不同，需要新机制。
- **第 1 档的现场 VAD 数据是本档的输入**：`VAD_SPEECH_RMS=0.02`、`VAD_SILENCE_RMS=0.01` 是起始值，展厅真实噪声地板与误触发率要在 P1 之前拿到实测。

## 3. 技术路线对比

| 路线 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. 自建 WebSocket 网关 + 流式 ASR/TTS 供应商** | 浏览器 `WebSocket` 传音频帧与文本；服务端代理到火山/讯飞/MiMo-realtime 等供应商的流式接口；TTS 输出按句回灌第 2 档的朗读队列 | 打断、部分识别、词级流水线全部可做；后端掌控会话与限流 | 新 Maven 依赖、新并发模型（与现有阻塞式 SSE 并存）、供应商选型与白名单变更、nginx 头 | **推荐** |
| **B. WebRTC + 服务端媒体处理** | 浏览器 WebRTC，服务端 SFU/STUN/TURN 或媒体服务器 | 回声消除、弱网、双工最标准 | 单机展厅、单客户端场景严重过度设计；引入媒体服务器运维面 | 不做 |
| **C. 分段滚动识别（REST 伪实时）** | 保持现有 HTTP：前端按 ~2s 滚动切段送 ASR，部分结果先上屏；朗读侧沿用第 2 档 | **后端近零改动**，纯前端即可验证展厅噪声下的端点检测与误触发 | 无插话；段间仍有缝；识别计费随段数上升；天花板低 | 作为 **P1 过渡**保留，不作为终点 |

**推荐：A，且用 C 的滚动识别先趟 P1。** 理由：打断与全双工只有 A 能给，而 A 的最大不确定性不是代码而是**展厅声学环境**——先用零后端改动的 C 在现场量出误触发/漏断的真实水平，再决定 A 的端点检测参数与供应商签约，风险最小。

## 4. 分期实施

### P1 — 流式/滚动 ASR 与端点检测（先测声学，再谈架构）
- 前端：滚动分段送识别（路线 C），部分识别结果先渲染在输入框/气泡；
- 端点检测从「前端 VAD 静音计数」升级为「前端 VAD + 服务端复核」双保险；
- 现场采集：噪声地板、误触发率（没人说话却开始录）、漏断率（说完不收尾）三组数据回填第 1 档常量；
- **出口物**：一份展厅声学实测报告 + 端点检测参数定稿。这份报告是 P3 立项的闸门。

### P2 — 流式 TTS 与 LLM 流水线衔接
- 第 2 档的句级队列（`beginAnswer/feedAnswer/endAnswer` + 预取循环）保持不变，升级数据源：从「等 SSE delta 攒句」改为「LLM 词级流出 → 按句切 → 合成」；
- 服务端若走 A 路线：WebSocket 下行文本帧复用同一套切句与预算（`MAX_SPEAK_CHARS`、`splitForSpeech` 口径不变）；
- 目标指标：一句话说完 → 首段音频 ≤ 1.5s（当前 = 一句生成 + 一句合成，通常 2~4s）。

### P3 — 插话打断（barge-in）
- 需求链：播放中检测到人声 → 停 TTS（清空朗读队列 + 暂停 Audio）→ 已听清的文本保留为新输入 → 进入新一轮识别；
- 回声消除：一体机喇叭与麦克风同机，必须依赖采集端 AEC（第 1 档已开 `echoCancellation`）+ 「播报期间的能量门限抬高」双层，否则自己的声音会打断自己；
- 与现有交互的合并：点按停读、chat「停」、VAD 自动收尾三条旧路径全部保留，打断只是第四条入口；
- **P1 报告不合格（误触发率高）则 P3 缩水为「仅手动打断」**，即现状，不硬上。

### 路线 A 落地时的先后顺序
P1（C 过渡）→ 确定供应商与实时端点 → 引入 WebSocket 通道（与现有 SSE 并存，`?voice=realtime` 灰度）→ P2 → P3。任何一步失败，回退开关就是回到第 1/2 档——那两档本身是完整的降级形态。

## 5. 基础设施改动清单（路线 A）

- [ ] `pom.xml`：`spring-boot-starter-websocket`（或等价），与现有 `sseExecutor` 并存的独立会话线程池；
- [ ] nginx：`proxy_set_header Upgrade/Connection` + 实时路径 `proxy_read_timeout`（deployment.md 补章节）；
- [ ] 限流：实时会话按「连接数 + 消息数」双维限流，复用 `RateLimiter` 抽象但换键（IP → 会话）；
- [ ] `/api/health`：新增 `realtimeReady`（供应商可达 + 通道启用），前端据此在实时/分段间自动降级；
- [ ] `tools/security.py`：新端点的边界用例（超长音频帧、未握手连接、消息洪水）；
- [ ] `tools/offline-check.py` / `AUDIO_PROVIDER`：新供应商出口白名单；
- [ ] `tools/loadtest.py`：实时通道的并发基线（当前基线只覆盖 HTTP SSE）；
- [ ] 会话与审计：实时会话的 chat_log 落库口径与 SSE 路径对齐（`logMessageMode=preview`，不落音频全文）。

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 开放展厅噪音/多人围观拾音 | 误触发、张冠李戴 | P1 先量再上；点按模式永久保留为兜底 |
| 供应商实时接口成本与配额 | 长连接按秒计费可能远高于按次 | P1 阶段就做成本测算；`speechSynthRateLimiter` 思路移植为会话配额 |
| 阻塞式 SSE 与实时通道并发 | 线程池争抢拖垮问答 | 实时通道独立线程池；`loadtest.py` 双通道同跑验证 |
| AEC 不彻底（一体机扬声器） | 打断时把自己声音当指令 | 能量门限 + 播报期间抑制 VAD；P3 验收单列此项 |
| 单通道故障拖死整个页面 | 大屏哑掉 | 实时通道失败自动回退第 1/2 档（`realtimeReady=false` 路径），与现有「服务端 TTS 失败降级浏览器合成」同款思路 |

## 7. 验收标准与回退

**验收（P3 完成时）：**
1. 说完一句话到听见回答首音 ≤ 1.5s（安静展厅实测 20 次取中位）；
2. 插话打断从开口到 TTS 静音 ≤ 300ms；
3. 空场噪声下 30 分钟误触发 ≤ 1 次（P1 报告同口径对比）；
4. 断网/供应商挂时页面自动回到第 1/2 档，麦克风与朗读按钮全程可用；
5. `tools/smoke.py`、`tools/security.py` 全绿，`loadtest.py` 双通道基线无回退。

**回退：** `VOICE_CHANNEL=segmented`（或 health 探测失败自动触发）回第 1/2 档；点按录音 + 整段识别 + 句级朗读是永不删除的最简形态。
