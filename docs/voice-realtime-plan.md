# 全双工实时语音（第 3 档）规划

规划文档，不含实现。目标是把语音问答从「点按 + 分段」升级到豆包语音模式那种**持续听、流式识别、边生成边播、随时插话**的全双工体验。本文只定路线、分期与验收口径；具体接口以选定供应商的文档为准。

前置：第 1 档（VAD 自动断句）、第 2 档（边流式边朗读）、第 3 档的 **P1（滚动分段识别 + 常开聆听 + 声学遥测）**
与 **P2.0 + P3a（四段延迟埋点 / 自适应阈值 / 分段管线抽取 / 插话打断）**均已落地，是本文的基线。
P1 的实现细节与逐条验收见 [archive/2026-10-12-voice-realtime-p1-plan.md](./archive/2026-10-12-voice-realtime-p1-plan.md)，
P1 留下的欠账收在 §5；P2.0/P3a 的逐条状态见 §4 里的两张状态表。

## 1. 目标与现状差距

| 能力 | 豆包语音模式 | 当前（P2.0 + P3a 之后） | 差距 |
|---|---|---|---|
| 触发 | 持续听，说话即始、停顿即止 | 常开聆听：首个手势后自动开麦，本地能量门控，VAD 停顿 ≈1s 自动收尾；说话阈值已**自适应底噪**（§5 S1） | 已很接近；差**服务端端点复核**（并入 P2.1） |
| 识别 | 流式，边说边出字 | 滚动分段（首段 2.8s、其后 2s 切片）+ 整段终稿：预览边说边出，终稿仍走整段 | 预览是**哑切**的、不是真流式（§5 S13）；首字延迟 ≈ 2s + 一次往返 |
| 回答开口 | 边生成边合成，1~2s 开口 | 攒够完整句即合成开播（第 2 档）；**四段延迟已各自可测**（说完→收尾→终稿→首句→首音） | 已接近；差**词级流水线**（当前最快 = 一句的生成 + 一句的合成） |
| 打断 | 说话即插话，AI 让口 | **P3a 已实现**：播报期间照采回声，持续越限即判插话 → 停播 + 掐掉在途回答 + 把这几块接成新一句；判决开关缺省关（门限待现场标定） | 粒度停在**分段**而非帧；帧级要等 P3b |
| 全双工通道 | 一条实时音频流 | 麦克风录音 / TTS 播放仍是两个互斥的 HTTP 时序 | 需要 WebSocket 或等价实时通道（P3b 才真正需要） |

## 2. 当前架构约束（事实，改动前先读）

- **后端是 Spring MVC + `SseEmitter` 阻塞式**（`ChatController` 的 `/api/chat/stream`，`sseExecutor` 独立线程池），全仓库 **没有任何 WebSocket / WebFlux / reactor 依赖**（`pom.xml` 只有 `spring-boot-starter-web`）。实时通道要从零引入。
- **MiMo 语音接口是整段 HTTP POST**（`MimoSpeechModel` 走 `/v1/chat/completions`）：ASR 收整段 WAV 回整段文本，TTS 收整段文本回整段 WAV，**均不支持流式**。流式 ASR/TTS 要么换供应商，要么确认 MiMo 是否提供 realtime 端点。
- **单机 Windows 一体机**：jar 自托管静态资源与 API，无外层网关；跨机访问才有 nginx，SSE 需要 `proxy_buffering off`，实时通道额外需要 `Upgrade`/`Connection` 头（deployment.md 尚未写这条）。
- **出口白名单**：`tools/offline-check.py` 维持「除 LLM、embedding、可选语音服务外一律本地」不变量；接新语音供应商 = 改白名单与 `AUDIO_PROVIDER` 语义（security.md 口径）。
- **麦克风依赖安全上下文**（HTTPS 或 localhost），`http://内网IP` 下按钮直接不出现（README 已有提示）。
- **限流现状**（P1 已改）：`chatRateLimiter` 30/min/IP（只作用于两个 chat 接口）、`asrRateLimiter` 120/min（`POST /api/speech/recognize` 独立）、`speechSynthRateLimiter` 60/min、`speechMetricsRateLimiter` 30/min；实时长连接的计费/限流维度与「每请求一次」完全不同，需要新机制（会话键而非 IP 键）。
- **第 1 档的现场 VAD 数据是本档的输入**：`VAD_SPEECH_RMS=0.02`、`VAD_SILENCE_RMS=0.01` 是起始值，展厅真实噪声地板与误触发率要在 P1 之前拿到实测——**P1 已经把采集通道建好**（前端 `useAcoustics` → `POST /api/speech/metrics` → `/api/stats` 的 `speech` 段 → `?admin=1` 面板），数据待现场跑；缺的那组（漏断率）见 §5 S3。

## 3. 技术路线对比

| 路线 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. 自建 WebSocket 网关 + 流式 ASR/TTS 供应商** | 浏览器 `WebSocket` 传音频帧与文本；服务端代理到火山/讯飞/MiMo-realtime 等供应商的流式接口；TTS 输出按句回灌第 2 档的朗读队列 | 打断、部分识别、词级流水线全部可做；后端掌控会话与限流 | 新 Maven 依赖、新并发模型（与现有阻塞式 SSE 并存）、供应商选型与白名单变更、nginx 头 | **推荐** |
| **B. WebRTC + 服务端媒体处理** | 浏览器 WebRTC，服务端 SFU/STUN/TURN 或媒体服务器 | 回声消除、弱网、双工最标准 | 单机展厅、单客户端场景严重过度设计；引入媒体服务器运维面 | 不做 |
| **C. 分段滚动识别（REST 伪实时）** | 保持现有 HTTP：前端按 ~2s 滚动切段送 ASR，部分结果先上屏；朗读侧沿用第 2 档 | **后端近零改动**，纯前端即可验证展厅噪声下的端点检测与误触发；**P1 之后连「插话打断」也能做一部分**（见 P3a：麦克风已常开、停播本就是毫秒级） | 段间仍有缝；识别计费随段数上升；打断只能到「分段粒度」，做不到帧级；天花板低 | P1 已按它交付；**天花板比原估计高**，但终点仍是 A |

**推荐：A，且用 C 走完了 P1。** 理由：帧级打断与真流式识别只有 A 能给，而 A 的最大不确定性不是代码而是**展厅声学环境**——所以先用零后端改动的 C 在现场把误触发/漏断量出来，再决定 A 的端点检测参数与供应商签约。

**据 P1 修订的一点：C 的天花板比原来估的高。** 原文把「打断」整块划给了 A，但打断的核心（检测人声 → 停 TTS → 接管输入）在 C 上就能做，只是粒度停在「分段」而非「帧」（见 §4 的 P3a/P3b）。这没有改变「终点是 A」的结论，但改变了顺序：**P3a 不必等供应商**，而它产出的回声地板数据恰恰是选型最需要的输入。

1. 在同一网关（`AUDIO_BASE_URL`）上探测 OpenAI 风格的实时端点是否存在：
   `GET/POST https://api.xiaomimimo.com/v1/realtime`（404 即没有；有些网关只在 WS 升级时才回 101）；
2. 看 MiMo 控制台/文档里 ASR 与 TTS 两条接口的入参有没有 `stream` / `chunk` / `partial` 字段；
3. 没有 → 直接比火山（豆包实时语音）与讯飞两家的：**是否支持双向流 + 打断事件 + 按音频秒计费**、
   并发会话上限、以及**出网域名能否进 `tools/offline-check.py` 的白名单**（换供应商 = 改白名单 +

**为什么这不挡路**：P2.0 的五项（三段延迟埋点、自适应阈值、`useSegmentStream` 抽取、成本口径、
本轮调研）与 P3a（分段通道上的打断）都已交付，**都不依赖这个结论**；而 P3a-1 采出来的回声数据
（`echo*` 那组计数）正是选型时判断「这家供应商的 AEC 够不够用」唯一靠得住的输入。
P2.1 与 P3b 仍然要等上面这次核对，顺序见 §4 的落地顺序。

### P2 — 流式 TTS 与 LLM 流水线衔接（据 P1 实际修订）

- 第 2 档的句级队列（`beginAnswer/feedAnswer/endAnswer` + 预取循环）保持不变，升级数据源：从「等 SSE delta 攒句」改为「LLM 词级流出 → 按句切 → 合成」；
- 服务端若走 A 路线：WebSocket 下行文本帧复用同一套切句与预算（`MAX_SPEAK_CHARS`、`splitForSpeech` 口径不变）。

**据 P1 的四处修订：**

1. **目标指标拆成三段，别用一个数。** 原文「一句话说完 → 首段音频 ≤1.5s」把三段延迟混在一起（说完→终稿文本、终稿→首句生成、首句→首段音频），测出超标也不知道该优化谁。改为分开记、分开验收：
   - 说完 → 终稿文本 **≤ 1.2s**（今天 ≈ VAD 静音 1s + 整段识别往返）
   - 终稿 → 首句生成 **≤ 1.0s**
   - 首句 → 首段音频 **≤ 0.5s**
   三段都要能单独看到，所以 **P2.0 先把埋点补上**（§5 S4/S8）。
2. **「服务端端点复核」从 P1 的遗留项并入 P2。** P1 没做它，现在也不该在 P1 补：REST 分段下要做服务端复核就得把音频再传一遍，收益不抵成本；而 P2 若走 WebSocket，音频帧本来就由服务端收，端点检测自然下沉。**放对了地方才成立**。
3. **抑制粒度要跟着播报变碎一起调。** P1 的抑制是「整段播报期间冻结，并放弃正在说的语句」（`setSuppressed`）。P2 让播报按更短的片段滚动 → 抑制/恢复切换更频繁 → 正在说的句子被反复放弃。P2 应把抑制从「按播报状态」改成「按回声能量」（门限自适应，见 §5 S1）。
4. **合成限流要重估。** `AUDIO_SYNTH_RATE_PER_MIN=60` 是按「一句一合成」定的；词级流水线会把片段切得更碎、合成次数上升，需要按实测重定，或给合成也上「按音频秒」的配额。

### P3 — 插话打断（barge-in）：拆成 P3a / P3b

**据 P1 的关键修订：P3 不必等 P2，也不必等 WebSocket。** 打断的核心链路是「检测到人声 → 停 TTS → 已听清的文本作为新输入」，而三件事**今天都已经有了**：麦克风常开（P1 的 `arm()`）、`speech.stop()` 毫秒级停播（第 2 档：清队列 + `pause()` + `cancel()`）、分段预览当「已听清的文本」（P1 的 `onPartial`）。原计划把 P3 排在实时通道之后，是把它和「低延迟打断」混为一谈了。

> **状态（2026-10-12）：P3a 两条都已落地，P3a-2 的门限待现场标定。**
>
> | P3a 条目 | 状态 |
> |---|---|
> | P3a-1 只测不判（拿回声地板数据） | ✅ **缺省形态**：播报期间语句/VAD/底噪仍冻结，但照采回声；新增 `echo*` 计数与 `avgEchoRms/avgEchoDb/echoOverRate/echoFarOverRate`，运营面板可见 |
> | P3a-2 真打断（判决） | ✅ 机制交付：持续 `BARGEIN_HOLD_MS`（120ms）越限 `speechThreshold × BARGEIN_FACTOR`（2 倍）→ 解除抑制 + 回灌那几块成新句 + 停播并掐掉在途回答。**开关缺省关**（运营视图 `znwd.bargein`），门限与持续时长按默认值先落地、由现场回声数据标定 |
> | 「已听清的文本作为新输入」 | ✅ 实现为「回灌成新一句」：插话的那几块接成新句的开头，走一遍 VAD（否则「哼一声就停」会挂到 20 秒上限），终稿照旧自动提问 |
> | 与三条旧路径合并 | ✅ 点按停读、chat「停」、VAD 自动收尾全部保留，打断只是第四条入口 |

**P3a —— 分段通道上的打断（纯前端，现在可做）**

- 把 P1 的**抑制控制器换成打断控制器**，同一个入口 `setSuppressed`，只换判决：
  - 今天：`chat.streaming || speech.speaking` → 无条件冻结；
  - P3a：播报期间**仍然听**，但门限抬到「回声门限」；越过门限并持续 X ms → 判为人声插话 → `speech.stop()` → 保留当前 partial 作为新一轮输入 → 重新起句。
  - 低于门限时**保持抑制**：不打断、也不污染底噪采样。
- **先量后判**，分两步落地，第一步零风险：
  - **P3a-1（只测不判）**：播报期间照常采样，但只上报、不定判决。拿到「自己的喇叭声在麦克风里到底多响、AEC 之后还剩多少」这组数——今天因为一律冻结，这组数**根本采不到**。
  - **P3a-2（真打断）**：按 P3a-1 与 P1 报告的数据定门限与 X，打开判决。
- 判据（抬高多少 dB、持续多少 ms）**必须由现场数据定**，不能拍脑袋——这正是 P1 出口物要用到的地方。
- 与现有交互合并：点按停读、chat「停」、VAD 自动收尾三条旧路径全部保留，打断只是第四条入口。

**P3b —— 实时通道上的低延迟打断**

- 把 P3a 的判决搬到服务端（音频帧由服务端收，端点检测与回声抑制都在服务端做），把打断延迟从「分段粒度」降到「帧粒度」；依赖 P3a 的现场数据与供应商选型，不能提前做。

**验收指标的归属（原文写在「P3 完成时」，实际分属不同阶段）：**

| 指标 | 何时可验 |
|---|---|
| 空场噪声 30 分钟误触发 ≤ 1 次 | **现在就能验**（P1 的遥测通道） |
| 插话打断 → TTS 静音 ≤ 300ms | **P3a** 即可验（`speech.stop()` 本身就是毫秒级） |
| 说完 → 首音 ≤ 1.5s | 需 **P2** |
| 断网/供应商挂自动回退第 1/2 档 | 现在就有（`speechReady` + 降级路径）；实时通道上线时按同款思路补 `realtimeReady` |

**P1 报告不合格（误触发率高）则 P3 缩水为「仅手动打断」**，即现状，不硬上。

### 落地顺序（据 P1 修订）

```
P1（已完成）
  ├─ P2.0 + P3a（不依赖供应商）               ← 已完成（2026-10-12）
  ├─ 确定供应商与实时端点（§3.1：待一次有网络的手工核对）
  ├─ WebSocket 通道（与现有 SSE 并存，?voice=realtime 灰度）
  ├─ P2.1（真流式 ASR/TTS + 词级流水线）
  └─ P3b（帧粒度打断）
```

关键改动是**把「等供应商」这件事从关键路径上挪开**：P2.0 的埋点、P3a 的回声测量与打断判决、
§5 里那批小修，全都不依赖选型，而且它们产出的正是选型最需要的现场数据——**这一条已经从「计划」
变成了既成事实**（见上面两张状态表）。任何一步失败，回退开关就是回到第 1/2 档——那两档本身是
完整的降级形态，P1 之后还多了一层「常开聆听可关，退回点按」，P3a 之后再多一层「插话判决可关，
退回只采回声」。

## 5. P1 遗留短板与优化项

P1 的代码已落地，但它在**现场数据闭环**与**分段质量**上留了一批明确的欠账。按「做它的理由」分三组，组内顺序就是建议的动手顺序。每条都只写能被单测或现场数据验住的部分，不列「顺手也可以」的偏好项。

> **状态（2026-10-12，P2.0 + P3a 本轮）**：**S1 / S3 / S4 / S5 / S8 / S14 / S15 已落地**（逐条见
> `CHANGELOG.md` 对应小节；S15 落成一条前端断言「计数键 ⊆ 后端白名单」，直接读 `SpeechParser.java`）。
> 其余待做，其中 **S2（噪声样本口径与分位数）** 是 §5.1 里最后一条影响报告可信度的：
> 底噪已经能自适应（S1），但「这份底噪数本身可不可信」还只报均值——`echo*` 那组计数用的是
> 「越限块数比例」而不是均值，正是为了不重蹈 S2 的覆辙，S2 本身的范围与修法不变。

### 5.1 数据闭环（P1 出口物「展厅声学实测报告 + 参数定稿」的必需品）

| 编号 | 短板 | 为什么算短板 | 修法 | 成本 |
|---|---|---|---|---|
| S1 | **底噪没有回流成自适应阈值** | 底噪已经在上报（`noiseFloorSum/noiseSamples`），但 `VAD_SPEECH_RMS` 到用的时候仍是常量——采了不用，等于只买了报告、没买结论 | 前端维护「安静块 RMS 的滑动 EMA」，阈值取 `max(常量, ema × k)`；服务端那份仍作报告口径 | 小 |
| S2 | **噪声样本口径混杂，且只报均值** | 所有非人声块混在一起，而展厅里绝大多数样本其实是「有人说话时的静音尾巴」；均值又对偶发大噪声不敏感——调阈值要看的是 **p50/p90** | noise 事件带状态标签（聆听态 / 语句静音尾巴），或改成对数分桶上报、服务端算分位数 | 中（动遥测白名单与运营面板） |
| S3 | **缺「漏断率」** | P1 要的是三组数据（噪声地板 / 误触发率 / 漏断率），现在只有前两组；「一句被静音阈值截成两句」从数据上分辨不出来 | `auto` 结束后 1.5s 内又起了一句 → 计一次「疑似漏断」。**落地时补了两个排除条件**：该句终稿确实识出了文字（回空的是误触发）、那一句不是插话——不然嘈杂展厅的漏断率会失真 | 小 |
| S4 | **终稿端到端延迟没上报** | `/api/speech/recognize` 回的 `elapsedMs` 前端拿到了却没用；而「说完 → 提问发出」才是参观者真正感知的那段延迟 | 终稿落地时上报一次耗时 | 小 |

### 5.2 体验与成本（不依赖供应商，随手可做）

| 编号 | 短板 | 为什么算短板 | 修法 | 成本 |
|---|---|---|---|---|
| S5 | **短句白发一段分段识别** | `accumulateSegment` 把静音块也算进切片：语音 1.5s 的短句在 t≈2.05s 就发出一段（含 0.55s 静音），而语句 t≈2.5s 结束 → 预览与终稿几乎同时落地，**白花一次调用 + 输入框闪一下** | 两条都做了：首段门槛抬到 **2.8s**（直接消掉短句那次调用），占比过滤按**自适应阈值**算（0.4）——按「有动静」算的话在真实展厅恒等于没写 | 小 |
| S6 | **超限是整段丢弃** | `MAX_SEGMENT_INFLIGHT=2` 超了直接扔 2 秒音频 → 网络一抖预览就出现空洞（文字跳一段） | 改成积压合并：超限的那段并进下一段一起发，延迟涨、内容不丢 | 小 |
| S7 | **连续 429 不降级** | 配额长期打满时每段都在白打一次 429，运营只看到 `segmentFailures` 在涨 | 连续 N 次失败 → 本会话停分段、只留终稿，并在上报里带标记 | 小 |
| S8 | **成本没有口径** | §7 要求「P1 阶段做成本测算」，但只上报了**调用次数**——ASR/TTS 多按**音频秒**计费 | segment 与终稿事件各带一次音频时长 | 小 |
| S9 | **闭馆后还在听** | 闲置复位只清对话、不动麦克风：过夜时保洁与空调噪声照样起句、照样打 ASR、照样刷错误日志 | N 分钟无交互 → disarm，下一次手势自动恢复 | 小 |
| S10 | **预览直接改写输入框** | 参观者手打时语音预览会覆盖草稿（P1 计划里承认的边界情况，展厅可接受，演示场景会打架） | 预览改成「半透明前缀/气泡」，或用户一旦手动编辑过就不再覆盖 | 小 |
| S11 | **没有实时音量反馈** | 只有一个 `on` 类和一句文案。参观者不知道「它在听我吗、声音够不够」 | 按钮上加一条 RMS 条（`chunkRms` 已经在算）：既回答这个疑问，也把现场调阈值**可视化** | 小 |
| S12 | **界面缺一句隐私说明** | 麦克风常开 + 大屏，却没说「语音不会被保存」（后端确实只记长度、不记内容） | 常驻一句说明 | 极小 |

### 5.3 质量与结构（P2 动工之前做）

| 编号 | 短板 | 为什么算短板 | 修法 | 成本 |
|---|---|---|---|---|
| S13 | **分段是「哑切」** | 固定 2s 硬切、不重叠、带静音尾巴：切片落在词中间就会识出半个词（预览抖动），边界处最容易丢字 | 按 VAD 静音边界切 + 200~300ms 重叠 + 最长公共前后缀去重。**若 P2 走真流式，这条降级为「C 路线当终点时的优化」** | 中 |
| S14 | **`useDictation` 已在失控的路上** | 792 行、43 个模块级绑定，两个模式与分段管线耦合在一起；P2/P3 还要继续往上加 | 分段管线（`segmentChunks/segmentSamples/segmentInflight/segmentControllers/partialText/utteranceId` + `accumulateSegment/sendSegment/abortSegments`）整块抽成 `useSegmentStream` | 中 |
| S15 | **遥测事件与计数键是两份手写清单** | `useAcoustics.accumulate` 与后端 `SpeechParser.METRIC_KEYS` 各写一遍：加事件忘了加键就是**静默丢数据**，没有报错也没有日志 | 测试里断言「前端产出的键集合 ⊆ 后端白名单」 | 极小 |
| S16 | **遥测不落库 → 一周趋势看不到** | 内存计数、重启清零是**有意为之**（体检数据不是账目，理由见 `docs/api.md`），但「这一周的底噪趋势」因此没有出处 | 折中：每次 flush 的增量顺手 `JsonlStore.append` 一条，零 schema 变更即可留痕 | 小 |

> **优先级**：S3 补上三组数据里缺的那一组、S1 让底噪真正参与判决（否则只是「采了不用」）、S2 让这份底噪数可信——这三条直接决定 P1 出口物（声学报告 + 参数定稿）能不能交。S4/S5 排在它们后面但别拖太久：S4 是被测的量本身，S5 影响那段延迟，两者都决定 P2 的基线能不能测准。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 开放展厅噪音/多人围观拾音 | 误触发、张冠李戴 | P1 已把采集通道建好（`falseTriggers` 等，数据待现场跑）；P1 之后**点按模式与「常开聆听可关」是两级兜底** |
| 供应商实时接口成本与配额 | 长连接按秒计费可能远高于按次 | 先补音频秒数口径（§5 S8）再测算；`speechSynthRateLimiter` 思路移植为会话配额 |
| 阻塞式 SSE 与实时通道并发 | 线程池争抢拖垮问答 | 实时通道独立线程池；`loadtest.py` 双通道同跑验证 |
| AEC 不彻底（一体机扬声器） | 打断时把自己声音当指令 | P3a-1 先只测不判，拿到「回声地板」再定门限；低于门限保持抑制 |
| 单通道故障拖死整个页面 | 大屏哑掉 | 实时通道失败自动回退第 1/2 档（`realtimeReady=false` 路径），与现有「服务端 TTS 失败降级浏览器合成」同款思路 |
| 分段哑切导致预览质量差（§5 S13） | 参观者不信任预览、反而分心 | P2 走真流式则自然消失；不走则必须先做「按静音边界切」 |

## 8. 验收标准与回退

**验收（分阶段——三段延迟的具体数字见 §4 的 P2 修订 1，各条的归属见 P3 小节里的那张表）：**
1. 说完一句话到听见回答首音 ≤ 1.5s（安静展厅实测 20 次取中位）——**需 P2**（且先按三段各自记，见 §4 P2 修订 1）；
2. 插话打断从开口到 TTS 静音 ≤ 300ms——**P3a 即可验**；
3. 空场噪声下 30 分钟误触发 ≤ 1 次——**现在就能验**（P1 的遥测通道已经在报 `falseTriggers`）；
4. 断网/供应商挂时页面自动回到第 1/2 档，麦克风与朗读按钮全程可用；
5. `tools/smoke.py`、`tools/security.py` 全绿，`loadtest.py` 双通道基线无回退。

**回退：** `VOICE_CHANNEL=segmented`（或 health 探测失败自动触发）回第 1/2 档；点按录音 + 整段识别 + 句级朗读是永不删除的最简形态，P1 之后还多一层「常开聆听可关，退回点按」（`znwd.listen`）。
